PROJECT 03 / PRODUCTION SUPPORT

Bringing structure to incident response and technical triage.

A Spring Boot incident-management demonstration combining severity-based SLA targets, assignment and lifecycle transitions, activity history, rule-based log diagnostics and operational metrics.

01 / SYSTEM OVERVIEW

From alert to a traceable resolution.

The application models a support workflow: create an incident, assign an owner, acknowledge it, investigate, resolve and close it. It records lifecycle activity, calculates severity-based elapsed-time SLA targets and provides a deterministic diagnostic endpoint for log excerpts.

02 / ENGINEERING HIGHLIGHTS

What the system demonstrates.

01

Incident lifecycle

Supports incident creation, assignment, acknowledgement, in-progress work, resolution and closure.

02

Severity-based targets

Applies configured SLA targets by severity and reports elapsed-time status for the demonstration workflow.

03

Activity history

Records application-managed lifecycle events so the incident timeline can be reviewed.

04

Diagnostic triage

Uses deterministic keyword rules to classify supplied log excerpts and return a suggested category.

05

Persistence and migrations

Uses PostgreSQL with Flyway migrations and an H2-backed test path.

06

Operational visibility

Exposes application health and Prometheus-compatible metrics, with Swagger UI for API exploration.

06 / SCOPE & LIMITATIONS

What this project does—and doesn't claim.

The application is a local portfolio demo intended to show API design, persistence, workflow modeling and troubleshooting concepts. Its diagnostic output is advisory and its security model is intentionally limited.

  • Diagnostic analysis is keyword/rule-based, not AI-powered and not a substitute for log correlation or human investigation.
  • Demo Basic Auth credentials and local database settings must be replaced before any non-local deployment; no production RBAC/SSO is claimed.
  • SLA tracking is elapsed-time based; business calendars, pause policies and distributed scheduling are not implemented.
  • Activity history is application-managed and is not tamper-proof against direct database modification. High availability, disaster recovery and load testing are outside scope.

For implementation details, setup instructions, tests and current limitations, see the repository documentation.
